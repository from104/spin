# SPIN 요구사항 (확정본)

**SPIN** = *Strategy Planner for INclusive football*
파워체어 풋볼(전동휠체어 축구) 4v4 전술 보드 / 드릴 플래너.

원본 프로토타입: `docs/prototype/` (template.html = UI 마크업, logic.js = 상태·데이터).
프로토타입은 **순수 목업**이다 — 편집기 도구는 아이콘만 있고 동작하지 않으며,
드릴 6개·스텝 3개가 하드코딩되어 있고 저장/내보내기가 없다.
이 저장소의 목표는 그 컨셉을 **실제 동작하는 앱**으로 만드는 것이다.

## 1. 확정된 기술 결정

| 항목 | 결정 |
|---|---|
| 스택 | **React 19 + Vite + TypeScript** |
| 물리 | **matter.js** (2D 게임 물리 엔진) — 코트 위 모든 개체 |
| 저장 | **로컬 전용, 서버 없음**. IndexedDB(`idb`) + 드릴별 JSON 파일 내보내기/가져오기 |
| 렌더 | **SVG** (프로토타입과 동일). matter.js는 headless 물리로만 사용 |
| 배포 | 정적 빌드. 체육관 오프라인 사용 가정 (폰트·에셋 전부 번들 내장) |

## 2. 1차 버전 필수 범위

1. **편집기 실제 동작** — 코트 위 드래그 조작, 스텝 추가·복제·삭제
2. **드릴 CRUD + 라이브러리** — 생성·저장·복제·삭제, 카테고리 필터, 검색, 카드 썸네일 자동 생성
3. **시연 모드** — 전체화면, 큰 버튼, 화면 꺼짐 방지(Wake Lock), 스와이프 스텝 이동
4. **훈련 세션** — 드릴 여러 개를 순서대로 묶어 총 시간 계산, 세션 단위 시연

## 3. 코트 규격

프로토타입 좌표계를 유지한다. **월드 단위 = 미터**, 렌더 스케일 25 px/m.

코트 좌표의 **유일한 출처는 `src/model/court.ts` 의 `COURT_DEFS`/`courtDefFor` 다** — 아래 표는
그 값을 옮겨 적은 것이지 별개의 권위가 아니다(리터럴 금지 규칙. 2026-08-11 에 외곽선·센터
서클이 리터럴이라 마진을 넓히자 골대가 선 밖으로 나간 사고가 있었다).

| 모드 | 실제 규격 | viewBox | 경기면(SVG 좌표) |
|---|---|---|---|
| `full` 풀 코트 (최대) | 30 × 18 m | `0 0 825 525` | x 37.5..787.5, y 37.5..487.5 (750 × 450) |
| `full` 풀 코트 (표준) | 28 × 15 m | `0 0 775 450` | x 37.5..737.5, y 37.5..412.5 (700 × 375) |
| `full` 풀 코트 (최소) | 25 × 14 m | `0 0 700 425` | x 37.5..662.5, y 37.5..387.5 (625 × 350) |
| `half` 하프 코트 | 18 × 15 m, 90° 회전 | `0 0 525 450` | x 37.5..487.5, y 37.5..412.5 (450 × 375) |
| `flat` 플랫 코트 | 라인 없음 | `0 0 525 450` | 자유 배치 (viewBox 전체) |

**코트 마진은 1.5 m(37.5 px) 다** (2026-08-10 기현 지시로 1.0 → 1.5 m). 경기면 실치수는 그대로이고
viewBox 가 사방 12.5 px 씩 커졌다 — 마진은 코트를 줄이는 것이 아니라 판을 넓히는 것이다.
라인 밖 배치(킥인·코너 세트피스)에 휠체어(길이 1.5 m)가 온전히 서려면 1.0 m 로는 모자랐다.
옛 표의 `800 500` / `500 425` · `x 25..` 는 전부 마진 1.0 m 시절 값이다.

**풀 코트는 3단이다** (FIPFA Laws 2025 — 최대 30×18 / 표준 28×15 = 농구 코트 / 최소 25×14).
드릴이 `courtSize` 를 들고 다니고(스키마 v3), 기본값은 `'30x18'` 이다.
**하프·플랫은 3단을 따라가지 않는다** — Laws 에 하프 코트 규격이 없고, 따라가면 격자 5×3 의
칸 치수가 크기마다 달라져 "b2 로" 라는 말이 코트마다 다른 자리를 가리키게 된다
(근거 셋은 `court.ts` 의 `COURT_DEFS.half` 머리말에 전문이 있다).

파워체어 풋볼 규칙 요소:
- 골 지역 **2인 규칙** 존 하이라이트 (토글)
- 골포스트, 코너 컷, 페널티 마크(골라인에서 3.5 m)
- **코너킥 인크로치먼트 마크** (Laws 2025 신설 — 각 골포스트 안쪽 1 m. 풀 4개 · 하프 2개)
- **센터 마크** — 하프라인 중점의 15 cm "X". 풀 코트에만 있다
- ⚠️ **센터 서클은 없다.** Laws 2025 전문(50쪽)에 *"circle"* 이 0회 나온다 — 파워체어 풋볼에는
  센터 서클이 없다. 프로토타입 마크업에 있던 `r=75` 원은 5차(§5.3)에서 **삭제**했다

## 4. 물리 · 조작 요구사항 (핵심)

### 4.1 개체

| 개체 | 수량 | 비고 |
|---|---|---|
| 휠체어(선수) | 양팀 각 4 (GK 포함) | 아래 운동학 적용 |
| 공 | **최대 8개** | 트레이 상자에 "남은 개수" 로 표시된다 |
| 훈련 콘 | **색상별 8개** (= 코트 위 최대 16), **2가지 색** | 공과 같은 상자 은유라 개수 규칙도 같다 |
| 화살표 | 스텝당 최대 40 | route / pass 두 도구 |
| 메모(종이 쪽지) | 스텝당 최대 20 | 탭한 자리에 나타난다 |
| 스텝 | 드릴당 최대 60 | |

옛 표의 *"공 최대 10개 · 콘 제한 없음"* 은 2026-08-11 기현 지시(10 → 8, 콘 색상별 8)로
무효가 됐다. 수량의 유일한 출처는 `src/core/constants.ts` 의 `BALL.maxCount` ·
`CONE.maxCountPerColor` 다 — 편집기 배치 경로가 이 값을 본다.

> ⚠️ `src/model/validate.ts` 의 `LIMITS`(`maxBalls: 10` · `maxCones: 2000` · `maxSteps: 60` …)는
> **UI 상한이 아니라 깨진 파일 방어용 클램프**다. 두 숫자가 다른 것은 드리프트가 아니라 의도다:
> 남이 만든(또는 옛 버전이 만든) `.json` 을 읽을 때 10개짜리 공을 버리지 않고 받아 준다.
> 새로 놓을 수 있는 개수는 언제나 위 표다.

### 4.2 휠체어 회전축

- 회전축은 **차체 뒤 중앙에서 전체 길이의 1/5 지점** (= 탑승자 머리 위치).
- 즉 차체를 뒤(s=0) → 앞범퍼(s=L)로 볼 때 **피벗은 s = 0.2·L**.
- matter.js에서는 `Matter.Body.setCentre(body, offset, true)`로 회전 중심을 옮긴다.

### 4.3 드래그 4존 (차체 길이 방향 기준)

잡은 지점이 차체 어디냐에 따라 조작 방식이 달라진다.

| 존 | 위치 | 동작 |
|---|---|---|
| **후방 견인** | 피벗보다 뒤 | 뒤에 줄을 매달고 끌려가듯. 차체가 진행 방향을 따라 **자연스럽게 방향 전환**하며 후진 |
| **평행 이동** | 피벗(머리) 부근 | **방향 전환 없이** 그대로 평행 이동 |
| **제자리 회전** | 머리 ~ 앞범퍼 사이 | 피벗 고정, 축을 중심으로 **제자리 회전** |
| **전방 견인** | 앞범퍼 | 앞에 줄을 매달고 끌고 가듯. **자연스럽게 방향 전환**하며 전진 |

견인(tow) 동작은 로프/트레일러 운동학으로 구현한다: 잡은 점이 포인터를 추종하고,
피벗은 잡은 점으로부터 고정 거리를 유지하며 끌려온다. 차체 방향은 그 벡터에 정렬된다.

존 경계값은 **설정에서 조정 가능**해야 한다 (기본값은 설계 단계에서 확정).

### 4.4 속도 상한

- 전후진: **10 km/h** (= 2.778 m/s)
- 회전: **앞범퍼의 좌우 이동 속도 기준 30 km/h** (= 8.333 m/s)
  → 각속도 = 8.333 / (앞범퍼 ~ 피벗 거리). 조정 가능한 설정으로 노출할 것.

드래그 시 포인터가 아무리 빨라도 이 상한을 넘지 않게 프레임당 변위를 클램프한다.

### 4.5 충돌

휠체어끼리, 휠체어↔공, 휠체어↔콘 충돌이 물리적으로 자연스러워야 한다.
휠체어는 질량이 커서 공·콘을 밀어내고, 공·콘에 밀려나지 않는다.

## 5. 격자 오버레이 (토글 옵션)

실선 격자 + 칸 번호를 **흐릿하게** 표시. 열=알파벳, 행=숫자 (`a1`, `b4` …).

| 모드 | 격자 | 칸 번호 |
|---|---|---|
| `full` 풀 코트 | 가로 **6** × 세로 **5** 칸 | 칸마다 (`a1`…`f5`) |
| `half` 하프 코트 | 90° 회전 기준 가로 **5** × 세로 **3** 칸 (칸 크기 3.6 m × 5 m) | 칸마다 (`a1`…`e3`) |
| `flat` 플랫 코트 | **1 m 간격** 실선 격자 (+ 5 m 강조선) | 축 헤더 (`a`…`u` / `1`…`18`) |

**풀 코트의 칸 수는 크기 3단과 무관하게 6 × 5 다. 달라지는 것은 칸의 치수다**:

| 코트 크기 | 칸 크기 (m) | 칸 크기 (px) |
|---|---|---|
| 30 × 18 | 5.00 × 3.60 | 125 × 90 |
| 28 × 15 | 4.67 × 3.00 | 116.67 × 75 |
| 25 × 14 | 4.17 × 2.80 | 104.17 × 70 |

칸 수를 고정한 이유: 코치가 쓰는 말은 "a1 쪽" 이지 "5 m 칸" 이 아니다. 칸 수가 크기마다
달라지면 **같은 드릴을 다른 코트에서 설명할 수 없다**.

플랫 코트만 축 헤더인 이유: 1 m 격자는 21 × 18 = **378칸**이고 한 칸이 25 × 25 px 뿐이라
칸마다 라벨을 얹으면 판독 불가 노이즈가 된다. 스프레드시트처럼 가장자리에 열·행 머리글을 두면
코치가 `b4` 로 칸을 지목하는 것은 그대로 되면서 화면이 깨끗하다.
(요구사항 원문에서도 칸 번호 예시는 풀 코트 절에만 달려 있었다.)
→ 칸마다 표시하는 쪽을 원하시면 `src/render/GridOverlay.tsx` 의 모드 분기 한 줄로 되돌릴 수 있다.

> 옛 표의 *"20 × 17 = 340칸 · `a`…`t` / `1`…`17`"* 은 플랫 viewBox 가 500×425 이던 시절 값이다.
> 마진이 1.5 m 로 넓어지며 525×450 이 됐고, 1 m = 25 px 이므로 칸이 21 × 18 로 늘었다.

## 6. 저장

- **드릴 하나하나 따로** 저장·불러오기. 서버 없음.
- IndexedDB에 보관 + 개별 드릴을 `.json` 파일로 내보내기/가져오기.

**배송된 봉투 종류** (`src/storage/transfer.ts` — `ENVELOPE_VERSION` 은 1 그대로다):

| `spin` | 담는 것 | 상태 |
|---|---|---|
| `drill` | 드릴 1개 | 읽기·쓰기 |
| `session` | 세션 1개 + 그 세션이 참조하는 드릴들 | 읽기·쓰기 |
| `backup` | **드릴 전량 + 세션 전량 + 설정 + 자유 전술판** — 기기 이사 파일 | 읽기·쓰기 |
| `prefs` | 설정만 | **읽기만** (쓰는 곳 없음 — `backup` 이 대신한다) |
| `library` | 드릴 전량 | **읽기만** (4.7 에서 쓰기 중단 — 내보내기는 [보드] 하단 하나로 통합) |
| `drillSet` | 드릴 묶음 | 파싱만 되고 **커밋은 거부**한다 |

- **추후 예정** (1차 범위 아님, 데이터 구조에 여지만 남길 것):
  - 드릴 셋(여러 드릴 묶음) 기능 — 봉투 유니온에 자리만 있다
  - ~~설정 내보내기~~ → **`backup` 봉투로 배송됨**(4.7). 설정 단독 봉투(`prefs` kind)는
    일부러 만들지 않는다(`docs/PLAN-2026-08.md` §8) — 이 앱이 영구 저장하는 네 곳
    (IDB `drills` · IDB `sessions` · localStorage `spin.prefs` · localStorage `spin.board`)이
    한 파일에 전부 모이지 않으면 사용자는 "백업했다" 고 믿은 채 나머지를 잃는다

**그 밖의 내보내기** (파일이지만 앱이 도로 읽지는 않는 것):
- **PNG** — 한 스텝의 한 장면. 자립 SVG 문자열을 구워 래스터화한다
- **인쇄(PDF)** — `window.print()` + `@media print`. 세션 계획서 · 드릴 시트 두 종

### 7.1 화면 구조 — **5개 화면이 아니라 4개 화면 키 + 3단 레일이다**

옛 문장 *"5개 화면: 대문 / 목록 / 편집기 / 시연 / 설정"* 은 두 번의 재편으로 무효가 됐다.
사실은 `src/app/screens.ts` 가 갖고 있다:

| | 값 |
|---|---|
| 화면 키 (`Screen`) | `board` · `drills` · `present` · `settings` — **4개** |
| 레일 항목 (`RailKey`) | `board`(보드) · `drills`(드릴) · `settings`(설정) — **3개** |

- **2026-08-09**: `editor` 를 화면 키에서 **없앴다**. 자유 전술판과 드릴 편집은 같은
  컴포넌트(`EditorWorkspace`)이고 둘 다 `board` 자리에 뜬다 — 무엇이 떠 있는지는 화면 키가
  아니라 `AppShell` 의 `StageTarget`(`board | drill`)이 정한다. 옛 대문의 훈련 현황 대시보드는
  걷어냈고, `CourtPicker`(코트 선택 화면)는 은퇴했다.
- **2026-08-12**: `home` → `board`, `library` → `drills` 로 **개명만** 했다. 화면 키 수는
  그대로 4개다. 달라진 것은 **레일이 화면 키와 1:1 이 아니게 된 것**뿐이다 — `present` 는
  화면 키로 남되 레일에서는 빠지고(시연은 목록/카드에서 들어간다), 시연 중 레일 활성은
  `SCREEN_TO_RAIL` 이 [드릴]로 접는다.
- 옛 키(`home`/`library`)는 `LEGACY_SCREEN_KEYS` 가 한시적으로 받아 준다 — 열어 둔 탭의
  `history.state` 에 옛 키가 남아 있기 때문이다.
- 좁은 창에서는 세로 레일이 **헤더 좌측 3칸 세그먼트**로 접힌다. 같은 3항목·같은 아이콘이다.
- **인쇄 화면은 화면 키가 아니다.** `src/features/print/` 의 React 트리가 평소
  `display:none` 으로 붙어 있다가 `@media print` 에서만 보인다.
