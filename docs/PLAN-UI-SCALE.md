# PLAN-UI-SCALE — UI 크기 8단 + 자동, 레일 배치는 방향이 정한다

기현 지시(2026-09-18):
> "ui 크기 설정을 자동(비율, dpi에 따라 보드가 최대로 커지는 쪽으로), 50%, 75%, 100%, 125%, 150%, 175%, 200%"
> "ui비율이나 dpi가 낮아져도 가로화면은 무조건 레일이 왼쪽, 세로는 기존대로 위(아이콘만)으로 고정, 레일이 넘치면 스크롤 되게"

이 문서가 정본이다. 결정은 번호로 인용한다(`PLAN-UI-SCALE 결정 3`).

---

## §0 원칙

**이 기능은 새 설정이 아니라 기존 설정의 교체다.** `prefs.a11y.uiScale`(100/115/130%)이 이미 있고
(`src/storage/prefs.ts:62`), 그 기구는 루트 `font-size` 다(`src/app/App.tsx:34`). 값만 넓히면 지시를
이룰 수 없다 — 왜인지가 결정 1이다.

**측정하지 않은 것은 쓰지 않는다.** 배율 기구 셋은 추론이 아니라 에뮬레이터(iPad mini 규격,
CSS 1133×744)에서 진짜 입력을 쏴서 갈랐다. 표가 §1 결정 1 에 있다.

## §1 결정

### 결정 1 — 기구는 `transform: scale()`. `zoom` 도 `font-size` 도 아니다

| 기구 | 레이아웃 | gBCR ↔ 실제 클릭 좌표 | 판정 |
|---|---|---|---|
| 루트 `font-size` (현행) | rem 만 따라옴 | 일치 | **폐기** — px 고정값이 안 움직인다 |
| CSS `zoom` | 따라옴 | **어긋남**(배수 = zoom) | 기각 |
| 뷰포트 메타 동적 변경 | **무효** | — | 기각 |
| `transform: scale()` | 따라옴 | **일치** | **채택** |

- **현행 `font-size` 를 폐기하는 이유**: 레일 84(`AppRail.tsx:58`) · `--hit` 44 · 헤더 33 ·
  크롬 예산표 전체가 px 리터럴이다. 글자만 커지고 가구는 그대로라 **보드 크기가 거의 안 변한다** —
  지시의 "보드가 최대로 커지는 쪽"이 성립하지 않는다.
- **`zoom` 을 기각한 이유**(실측): zoom 1.5 에서 `getBoundingClientRect()` 는 **레이아웃 좌표**
  (41.5, 230)를 주는데, 그 요소를 실제로 누른 `pointerdown` 은 **시각 좌표** `clientX=62, clientY=345`
  로 도착한다. 배수가 정확히 zoom 이다. `clientX`/`clientY` 를 쓰는 파일이 **13개 약 50곳**이라
  전부 나눠야 하고, 하나만 빠뜨리면 코트 드래그가 **조용히** 어긋난다. 초록 테스트 뒤에 숨는 종류다.
- **뷰포트 메타를 기각한 이유**(실측): Capacitor WebView 에서 `content="width=…"` 를 런타임에 바꿔도
  `innerWidth`·`devicePixelRatio` 가 꿈쩍하지 않는다. 최초 로드에만 읽히는 것으로 보인다.
- **`transform` 을 채택한 이유**(실측): scale 1.5 에서 gBCR 중심 (62.3, 303.4)에 쏜 클릭이
  `clientX=62, clientY=303` 으로 도착했다 — **두 좌표계가 같다.** 항목 폭도 64 → 96 으로 커졌다.
  덕분에 위 13개 파일을 **한 줄도 안 건드린다**.

**대가 셋**(전부 유한하고, 아래 결정 6·7·8 이 갚는다): 미디어쿼리·`innerWidth` 가 배율을 모른다 ·
포털이 래퍼 밖으로 나간다 · 래퍼 안의 `vh/vw` 가 진짜 뷰포트를 가리킨다.

### 결정 2 — 값 집합과 마이그레이션

`uiScale: 'auto' | 0.5 | 0.75 | 1 | 1.25 | 1.5 | 1.75 | 2`. 기본값은 **`'auto'`**.

옛 값은 가장 가까운 새 값으로 옮긴다: `1 → 1`, `1.15 → 1.25`, `1.3 → 1.5`.
`CURRENT_PREFS_SCHEMA` 3 → **4**, `PREFS_MIGRATIONS`(`src/model/migrate.ts:336`)에 한 칸.

⚠️ 마이그레이션은 **의미가 바뀐다**: 옛 115% 는 «글자만 1.15배», 새 125% 는 «화면 전체 1.25배» 다.
숫자를 반올림하는 것이 아니라 **기구가 달라진 것**이라 체감이 다르다. 그래서 굳이 1.15→1.15 같은
값을 새로 만들지 않는다 — 없는 눈금을 남겨 두면 옛 기구의 유령이 남는다.

### 결정 3 — 「자동」은 **표적의 물리 크기**가 정한다

기현님 선택(2026-09-18). 후보 배율 중 **표적 44px 의 물리 크기가 기준선 이상이 되는 가장 작은 값**을
고른다 — 그 선 안에서 보드가 가장 커진다.

산술: `표적_mm = 44 × 배율 × (CSS px 1개의 물리 크기)`.

`CSS px 1개의 물리 크기`는 웹이 실제 ppi 를 안 알려주므로 **플랫폼 규약**을 쓴다:

| 플랫폼 | 1 CSS px | 근거 |
|---|---|---|
| 안드로이드(네이티브 셸·안드로이드 브라우저) | **1/160 in** | 1 CSS px = 1 dp, dp 의 정의가 1/160 in |
| 그 밖(데스크톱·기타) | **1/96 in** | CSS 규격의 기준 해상도 |

기준선 **9 mm**(ISO 9241-9 손끝 권고, Material 48dp ≈ 7.6mm 보다 보수적). 결과:

- 안드로이드: 100% = 7.0mm ✗ · 125% = 8.7mm ✗ · **150% = 10.5mm ✓** → 자동 = 150%
- 데스크톱: 75% = 8.7mm ✗ · **100% = 11.6mm ✓** → 자동 = 100%

⚠️ **이것은 근사다.** dp 는 실측 ppi 가 아니라 버킷이고(우리 7인치 AVD 는 320dpi 로 잡히지만 실물
아이패드 미니는 326ppi 다), 데스크톱의 1/96 은 OS 배율에 따라 흔들린다. 그래서 자동이 고른 값을
**설정 화면에 그대로 보여 준다**(「자동 (150%)」) — 사람이 틀렸다고 판단하면 즉시 고정값으로 덮을 수 있다.
숨은 자동은 «왜 이 기기만 이렇게 보이는가» 를 아무도 재현 못 하게 만든다(`useIsNarrow.ts` 머리말과 같은 이유).

### 결정 4 — 레일 배치는 `narrow` 가 아니라 **방향**이 정한다

- **가로(landscape)**: 항상 좌측 `AppRail`. 폭이 얼마든, 배율이 얼마든.
- **세로(portrait)**: 항상 상단 `AppNavSegment`, **아이콘만**(라벨은 `aria-label`·`title` 로 남긴다).

지금은 `AppShell.tsx:397` 의 `narrow`(폭 < 1100) 하나가 정한다. 이걸 `useIsPortrait()` 로 갈아끼운다.
**`narrow` 는 지우지 않는다** — 그쪽은 인스펙터 핀·팀 상세 2열(`TeamDetail.tsx:52`) 등 다른 계약이
계속 쓴다. 한 boolean 에 두 뜻을 담지 않는 것이 이 저장소의 규율이다(`useIsNarrow.ts` 머리말).

왜 방향인가: 배율 200% 나 낮은 dpi 에서 CSS 폭이 1100 아래로 떨어지면 **가로 화면인데 레일이
헤더로 접혔다**. 가로에서는 세로 공간이 귀하고 가로 공간이 남으므로 레일이 옳고, 세로에서는 반대다.
폭은 그 판단의 대리 변수였을 뿐이고, 배율이 생기면서 대리 변수가 거짓말을 하기 시작했다.

### 결정 5 — 레일이 넘치면 스크롤

`AppRail` 에 `overflowY: 'auto'` + 스크롤바 숨김. 숨김 관용구는 `AppNavSegment` 가 가로 넘침에
이미 쓰는 `.spin-nav-seg`(`styles/appShell.css`)와 **같은 것을 재사용**한다 — 두 벌을 만들지 않는다.
200% 에서 6칸 + 하단 묶음이 세로로 넘치는 것이 실제 촉발 조건이다.

### 결정 6 — 미디어쿼리를 배율 인식으로

`transform` 은 미디어쿼리를 안 바꾼다(실측: scale 1.5 에서 `mqNarrow` 가 false 그대로).
레이아웃 폭은 `innerWidth / s` 이므로 «레이아웃 폭 < 1100» ⟺ «`innerWidth` < 1100 × s».
`NARROW_QUERY` 를 배율을 받는 함수로 바꾼다. `matchMedia` 를 버리지 않는 것이 요점이다 —
문턱에서만 발화하는 성질이 코트 렌더 루프를 지키는 근거다(`useIsNarrow.ts` 머리말).

방향(`orientation`)은 균등 배율에 영향받지 않으므로 `useIsPortrait` 은 **그대로 둔다**.

크롬 예산의 뷰포트 공급원 `viewportSizePx()`(`src/app/useStageRot.ts:43`)도 `innerWidth/s` 를 낸다.

### 결정 7 — 포털은 래퍼 안으로

`Modal.tsx:159` 의 `createPortal(…, document.body)` 가 래퍼 **밖**이면 모달만 100% 로 남는다.
배율 래퍼를 포털 대상으로 넘긴다.

### 결정 8 — 래퍼 안의 `vh/vw` 는 래퍼 기준으로

`100vh/100vw` 는 래퍼가 아니라 진짜 뷰포트를 가리켜 배율만큼 넘친다. 10곳
(`appShell.css:23` · `Drawer.tsx:60` · `ToastHost.tsx:27` · `CenterModal.tsx:76-78` · `Modal.tsx:148` ·
`ChangelogModal.tsx:127` · `PresentRunner.tsx:526` · `ImportDialog.tsx:41`)을 `%` 또는
`calc(100vw / var(--ui-scale))` 로 바꾼다. 래퍼가 `--ui-scale` 을 심는다.

### 결정 9 — 크롬 예산의 `appRail` 행은 방향을 따른다

`CHROME_ROWS.appRail` 은 `narrow: 0`(좁으면 레일이 없다)을 전제한다. 결정 4 로 **가로면 항상 84,
세로면 0** 이 된다. `ChromeState` 에 방향을 넣고 `chromeRowPx` 의 레일 분기를 거기에 건다.
`now`(84)는 역사값이라 건드리지 않는다.

## §3 순서

1. **값과 저장** — prefs 타입·검증·마이그레이션·`uiScale.ts`(자동 산술). 화면 없이 테스트로 닫는다.
2. **기구** — 래퍼·`--ui-scale`·포털·`vh/vw`·미디어쿼리·뷰포트 공급원. 기존 3단이 새 기구로 도는 것까지.
3. **레일** — 방향 판정·세로 아이콘 전용·스크롤·예산 `appRail` 행.
4. **설정 화면** — 8단 + 「자동 (n%)」 표시, i18n 3벌.
5. **실기** — APK 굽고 7인치·10.1인치·iPad mini 규격 셋에서 §4.

## §4 실기 확인

- U-1 배율 8단을 돌리며 **레이아웃이 실제로 커지고 작아지는가**(글자만이 아니라 레일·헤더·바 전부)
- U-2 50% 에서 보드가 가장 크고, 200% 에서 가장 작은가
- U-3 **코트 위 드래그가 모든 배율에서 안 어긋나는가** — 결정 1 이 지키는 바로 그 지점
- U-4 모달·토스트·서랍이 배율을 따라오는가(결정 7·8)
- U-5 가로에서 배율 200%(= CSS 폭 566)에도 레일이 **왼쪽에 남는가**
- U-6 세로로 돌리면 상단 아이콘 바로 바뀌는가
- U-7 200% 에서 레일이 넘치면 **스크롤되는가**(잘리지 않는가)
- U-8 「자동」이 고른 값이 설정에 보이는가, 기기를 바꾸면 달라지는가
- U-9 전체화면 시연에서도 배율이 유지되는가
- U-10 배율을 바꾼 뒤 앱을 다시 켜도 유지되는가

## §5 남는 위험

- **`transform` 의 흐릿함**: 비정수 배율(125%·175%)에서 텍스트가 살짝 부드러워질 수 있다. 실기 U-1 에서 본다.
- **자동의 근사성**: 결정 3 의 ⚠️. 보이게 만드는 것으로 갚는다.
- **옛 설정의 체감 변화**: 결정 2 의 ⚠️. 변경 내역에 적는다.

## §6 실측 기록 (2026-09-18, iPad mini 규격 에뮬레이터)

구현 뒤 실제로 잰 값. **계획 단계의 추정과 어긋난 것을 여기 남긴다** — 계획서가 예언한 대로
됐는지가 다음 사람이 이 문서를 믿을지를 정한다.

### 기구는 의도대로 돈다

| 설정 | 레이아웃 크기 | 시각 크기 | 레일 실폭 | 레일 위치 |
|---|---|---|---|---|
| 50% | 2266×1352 | 1133×676 | 42px | 좌측 |
| 100% | 1133×676 | 1133×676 | 84px | 좌측 |
| 150%(= 안드로이드 자동) | 755×451 | 1133×676 | 126px | 좌측 |
| 200% | 566×338 | 1133×676 | 168px | 좌측(**스크롤 발생**) |
| 세로 | — | — | 0 | 상단 아이콘 줄 |

「자동」이 안드로이드에서 150% 를 고르는 것까지 실측 확인(결정 3 의 산술이 실제 기기에서 성립).

### ⚠️ 정정 — 작은 가로 화면의 회복 지점은 **75% 가 아니라 50%** 다

결정 4 로 물리 1024×600 에서 트레이가 4열 → 2열로 떨어지는데, 계획 단계에서는 "75% 로 갚는다"
고 적었다. **틀렸다.** 실측:

| 배율 | 트레이 폭 | 열 |
|---|---|---|
| 50% | 195 | **4열** |
| 75% | 141 | 2열 |
| 100% | 114 | 2열 |

이유: 코트가 **세로 제약**이라 배율을 낮춰 높이가 늘면 코트 폭이 `h×(825/525)` 로 **더 빠르게**
자란다 — 남는 폭(= 트레이 몫)이 오히려 줄어드는 구간이 있다. 폭과 높이가 같이 늘어난다고 해서
둘 사이의 여유가 같이 늘지는 않는다.

물리 800×480 은 **어떤 배율에서도 4열이 안 된다**(50% 에서도 124px, 2열).

### 결정 4 가 실제로 깬 것 (기현님 승인: *"그대로 간다 — 배율로 갚는다"*)

- 「1024×600 에서 스크롤이 사라진다」 완료 판정(§0.5) → **배율 50% 조건부**로 다시 적었다
  (`boardLayout.test.ts`).
- 「--hit 전환이 코트 축척을 안 건드린다」 불변식 → 1024×600 @100% 에서는 깨진다. 테스트를
  1365×800(=75%)으로 옮기고, **깨진다는 사실 자체**를 별도 it 으로 못박았다(`ToolRail.hit.test.tsx`).
