## 1. 이 문서의 용법

재편(2.1 개명 · 레일 3단 · NavEntry 확장 · 1.3 자가 분리)을 실행하면 아래 §3 표의 테스트들이

그건 회귀다.** 작업 중 예상 밖의 빨간불을 만나면 "재편 중이라 원래 깨지는 것"이라고 넘기지 말고,
먼저 이 표에 있는지 확인하라. 표에 없으면 그 커밋은 잘못 건드린 것이다. 표의 갱신 방법을 벗어나는
수정(특히 §4 의 수호 단언을 고치는 수정)도 회귀로 취급한다.

## 4. 수호 단언 — 절대 깨지면 안 되는 것 (0.4)

`src/app/screens.test.ts:13-18` 전문:

```ts
it("'editor' 는 더 이상 화면 키가 아니다", () => {
  // 2026-08-09 재편: 자유 전술판과 드릴 편집은 둘 다 home 자리에 뜬다(AppShell 의 StageTarget).
  // 이 단언이 없으면 어디선가 go('editor') 를 되살렸을 때 SCREEN_SET 이 걸러 조용히 무시하고,
  // 화면이 안 바뀌는 이유를 찾기 어려워진다.
  expect(SCREEN_ORDER).not.toContain('editor');
});
```

이것이 **이 안(안 1, Board-First)이 안 2(화면 분리안)와 갈리는 유일한 구조적 분기의 수호선**이다.
안 2 는 `board`/`edit` 로 화면 키를 쪼개며 2026-08-09 의 "editor 를 별도 화면 키에서 없앴다"
결정을 되돌리려 했다(계획서 2.1 원칙 1). 채택안은 개명만 하고 화면 키를 늘리지 않으므로,
`SCREEN_ORDER` 가 `['board','drills','present','settings']` 가 돼도 이 it 은 `SCREEN_ORDER` 와
문자열 `'editor'` 만 참조해 **손대지 않은 채** 통과한다.

**재편의 어느 커밋에서든 이 it() 을 수정하거나 삭제하는 diff 가 나타나면, 그 커밋은 안 2 로
미끄러진 것이다. 갱신 대상이 아니라 판정 기준이다.**

### 14.3 포커스 계약 [D-5] — 확정

`ui/Drawer.tsx`(세션 드로어, §6.11 *"편집기 인스펙터와 같은 시각 언어"*)의 계약을 그대로 따랐다.

1. **비모달.** 오버레이는 `role="dialog" aria-modal="false"`, **포커스 트랩 없음**. 판의
   동반자라 속성을 고치고 곧바로 코트·트레이로 Tab 해 나가야 한다. 붙박이일 때는 `role` 자체를
   벗는다(자리를 가진 영역이지 대화상자가 아니다).
2. **열면 제목(h2 tabIndex=-1)으로 포커스, 닫으면 트리거로 복귀**(§7.6 세션 드로어 행).
   복귀 대상은 **설치 시점에** 잡고 `isConnected` 일 때만 되돌린다 — 화면 전환으로 편집기째
   사라질 때 떼어진 버튼에 focus() 를 걸면 §7.6 의 `<main>` 포커스를 `<body>` 로 지운다.
3. **Esc 우선순위 = 모달 > 시트 > 선택 해제.** 1.7 이 Esc 를 전역 '선택 해제'로 넣었으므로
   겹친다. 이 순서는 플래그가 아니라 **등록 단계**가 정한다:
   - 모달(`ui/Modal.tsx`)은 document **캡처**에서 `stopPropagation` → 시트의 루트 요소(타깃
     단계)까지 내려오지 않는다.
   - 시트는 **자기 루트 요소**에만 리스너를 단다 → *포커스가 시트 안일 때만* 먹고,
     먹으면 `stopPropagation` 으로 선택 해제를 막는다(속성을 고치다 선택이 풀리면 패널이 빈다).
   - 입력(INPUT/TEXTAREA/SELECT) 중에는 먹지 않는다 — IME 조합 취소를 빼앗지 않는다.
   테스트는 세 소비자를 **실제 등록 지점**에 세워 두고 본다(캡처 대역·버블 대역·시트).

## 16. 2.3 `useIsNarrow` + 크롬 예산 (§5.1~5.3) — 착수 후 기록 (2026-08-12)

### 16.1 새로 '의도적으로 깨질' 것 — 3건 (사전 등록)

크롬 예산은 **소스와 이어져 있어야 산다.** 표를 문서에만 두면 다음 사람이 한 행을 줄일 때
합계가 맞는지 확인할 길이 없고, 몇 달 뒤에는 표와 코드 중 어느 쪽이 참인지도 모른다. 그래서
`chromeBudget.test.ts` 의 마지막 describe 가 소스 텍스트를 직접 읽어 '현재' 열과 대조한다.
**아래 셋은 담당 항목이 값을 바꾸는 순간 반드시 빨간불이 된다. 그건 회귀가 아니라 신호다** —
테스트를 지우지 말고 `CHROME_ROWS` 의 그 행을 함께 고쳐라.

| 언제 깨지나 | 무엇이 | 어떻게 갱신하나 |
|---|---|---|
| **2.4** 가 트레이 칩을 44px 로 키울 때 | `chromeBudget.test.ts` — *'트레이 폭 78 …'* (ToolRail.tsx 의 `width: 78` 을 읽는다) | `toolRail` 행의 **`now` 를 새 실측값으로**. `wide`/`narrow` 는 이미 93 이므로 건드리지 마라 — 예산 합계 117·538 은 그 93 으로 이미 계산돼 있다 |
| **2.4** 가 트레이를 키울 때 | `EditorWorkspace.narrow.test.tsx` — 해시 · 뼈대 스냅샷 (트레이가 `<main>` 안에 있다) | 새 DOM 으로 해시·스냅샷을 다시 뜨고, 커밋 메시지에 *"트레이 93 반영"* 을 적어라. **뼈대 diff 에 트레이 말고 다른 줄이 함께 움직였다면 그건 회귀다** |
| **2.10** 이 TransportBar 를 64 로 줄일 때 | (테스트는 없다 — 높이가 단일 리터럴이 아니라 합성값이라 텍스트로 못 건다) | `transportBar` 행의 `now`/`wide` 를 실측으로 갱신. 세로 합계 132 는 이미 64 로 계산돼 있다 |

앞의 둘은 **같은 변경에 함께 깨진다.** 하나만 초록불이 되면 값 갱신을 반쪽만 한 것이다.

### 16.2 완료 판정 *"narrow === false 스냅샷이 현재와 바이트 동일"* 을 관측 가능하게 만든 방법

이 판정의 전부는 **순서**다. 구현을 얹은 뒤에 뜬 스냅샷은 증거가 아니라 자기 자신의 사본이다.
그래서 소스를 한 줄도 고치기 전에 `EditorWorkspace.narrow.test.tsx` 를 먼저 만들어
2.3 **이전 코드**로 두 값을 떴다:

| 층 | 무엇 | 왜 둘 다 필요한가 |
|---|---|---|
| 해시 | `<main>` 전체(29KB) 의 sha256 | "정확히 같은가" 에 애매한 답이 없다. 대신 깨지면 diff 가 안 나온다 |
| 뼈대 스냅샷 | 상자들의 인라인 style 만 뽑은 목록(코트 `<svg>` 안쪽 제외) | 해시가 깨졌을 때 *어디가* 달라졌는지 읽게 해 준다. 대신 이것만 두면 느슨하다 |

`<svg>` 안쪽을 뼈대에서 뺀 이유: 거기까지 넣으면 좌표 한 자리만 바뀌어도 이 테스트가 대신
빨간불이 되어 **크롬 예산이 깨진 것인지 코트가 바뀐 것인지 구별할 수 없다.** 해시는 전체를
보므로 느슨해지지 않는다.

**곁가지 — 해시가 전체 스위트에서만 가끔 흔들렸다.** 파일 하나만 돌리면 늘 맞는데 1219개를
함께 돌리면 4회 중 1회꼴로 어긋났다. 원인은 `TransformWriter` 가 rAF 로 `transform` 을 DOM 에
직접 쓰는 구조다(§6.1 규칙 1) — 부하가 걸리면 첫 프레임이 오기 전에 DOM 을 읽어 골대 4개의
`transform` 속성이 통째로 없는 상태가 잡혔다. 골대 transform 을 기다린 뒤 읽도록 고쳤고
전체 스위트 4회 연속 바이트 동일을 확인했다. **부하에서만 나오는 흔들림은 "가끔 빨간불"이
아니라 계약이 시간에 의존한다는 뜻이다** — 다음에 이 판을 통째로 스냅샷 뜨는 사람은 같은
자리를 밟는다.

### 16.3 계획서 지시에서 벗어난 것 — 2건

1. **배선은 코트 래퍼 패딩 한 행만 했다.** §5.2 표의 나머지 행은 담당 항목이 따로 있고
   (트레이 2.4 · 하단 바 2.10 · 인스펙터 2.2 완료), 남의 행을 미리 줄이면 그쪽 완료 판정이
   내 커밋에 먹힌다. 2.3 이 내놓는 것은 **자**와 **boolean** 이고, 값이 여기 있으니 조치가 아직
   안 온 행도 예산에서는 이미 보인다.
2. **`appRail`·`appHeader` 행의 owner 를 '미지정' 으로 적었다.** 2차 표에 *"레일 84→0(헤더 좌측
   세그먼트로 접는다)"* 과 *"헤더 62→52(코트 세그먼트·주 액션을 하단 바로 이관)"* 를 실제로
   할 행이 없다 — §5.2 산문에만 있다. 폭 예산에서 걷어내기로 한 84 가 통째로 그 미지정 행이다.
   **레일이 남아도 1024×600 의 확정 배율 0.8914 자체는 버틴다**(상자가 823×468 이 되는데 세로가
   제약이라 468/525 는 그대로다) — 그래서 이 구멍은 축척 표로는 안 보인다. 대신 §5.4 의
   *"남는 폭 172px"* 이 88px 로 줄어 **트레이를 93 이상으로 넓힐 여력이 사라진다**(2.4 가 `--hit`
   56 을 켜면 117 이 필요하다). **2차 표에 행을 세우거나 3차로 명시 이월하라.**

### 16.4 [A-13] half/flat — 원안 표가 놓친 것

원안 §5.3 은 `min(boxW/825, boxH/525)` 로 **풀 코트만** 계산했다. half/flat 은 525×450 이라 같은
상자에서 다른 답이 나온다(1024×600 좁은 창: full 0.8914 · half 1.0400 · flat 은 half 와 동일 —
D12 가 viewBox 를 같게 못박고 있다).

정정의 핵심은 숫자가 아니라 **이득의 출처**다:

| | 재편 전 제약 | 좁은 창 이득 | 왜 |
|---|---|---|---|
| 풀 코트 | **폭**(501/825 < 404/525) | +46.8% | 폭 예산 523→117 이 그대로 이득이 된다 |
| 하프·플랫 | **세로**(404/450 < 501/525) | +15.8% | 폭을 아무리 벌어도 안 커진다. 세로 예산 196→132 만큼(468/404)만 커진다 |

즉 §5.3 의 *"half/flat 은 narrow 가로에서 세로 제약이 더 심하다"* 는 서술은 **방향은 맞고 결론이
반쪽**이다 — 하프가 세로에 갇히는 것은 맞지만 그래서 축척이 작아지는 것이 아니라(하프가 절대값은
더 크다) **크롬 예산을 줄여도 덜 커진다.** 하프를 주로 쓰는 사람에게 이번 재편의 체감은 풀 코트의
1/3 이다. 하프 사용자를 더 키우려면 손댈 곳은 폭이 아니라 **세로 132**(헤더 52·하단 바 64)다.

### 16.5 [A-12] safe-area — 왜 '더하기' 인가

`#root` 가 `env(safe-area-inset-*)` 를 **패딩으로** 먹는다(appShell.css). 그러므로 이 여백은 어느

## 19. 2.6 마진 띠를 잡으면 판이 움직인다 + Ctrl+방향 팬 (P2-1) — 착수 후 기록 (2026-08-12)

§3 표의 사전 등록은 한 줄도 밟지 않았다(2.6 은 등록된 항목이 없다). **단언이 바뀐 기존
테스트는 0건**이다 — 아래 §19.5 의 세 파일은 새 필수 필드를 채운 **타입 스텁 추가**이고
단언은 한 줄도 손대지 않았다.

### 19.1 이 항목의 본론 — `edgePanBandPx = 56` 충돌을 어떻게 닫았나

심사관 1 이 [치명]으로 짚은 것은 "왼쪽 56px 이 겹친다" 가 아니다. 마진 띠는 **1.5 m =
37.5 월드px** 이고 edgePan 띠는 **56 CSS px** 이라, 100% 배율(pxPerUnit ≈ 0.66~1.7)에서
마진 전체가 edgePan 띠 안에 통째로 들어간다. 네 변 모두 그렇다.

닫는 방식은 **시작 지점으로 나누기**다. 두 기능이 같은 화면 자리를 두고 다투게 두지 않는다:

| 어디서 pointerdown 했나 | 무엇이 시작되나 | edgePan |
|---|---|---|
| 경기면(surface) 안 · 개체 없음 | 고무줄 선택 | **켠다** |
| 경기면 밖 마진 · 개체 없음 | 판 이동 | **끄고** 시작조차 안 한다 |
| 어디든 · 개체 있음 | 그 개체 드래그 | 끈다(기존 계약) |

edgePan 은 *고무줄이 이미 시작된 뒤에* 도는 기능이므로 그대로 유효하다 — 첫 행이 그 근거다.
`framePan.test.tsx` 가 두 행을 **한 it 안에서** 갈라 단언한다(`pan` 이 참이면 `edgePan` 은
거짓이어야 한다). 반증 F3 이 이 한 줄만 찔러 1 it 을 빨간불로 만든다.

### 19.2 순서가 규칙의 전부다 — `hitTest` **뒤**에 좌표를 본다

마진에는 개체가 정당하게 서 있다(킥인·코너 세트피스, D26 — 마진을 1.0 → 1.5 m 로 넓힌
2026-08-10 지시의 이유가 바로 그것이다). 그래서 판정은 **히트테스트가 먼저**다:

```
hit = hitTest(world, …)
if (!hit) {                       // 잡을 것이 없을 때만 좌표를 본다
  if (!isOnSurface(mode, world)) return { pan: true };
  …고무줄…
}
```

순서를 뒤집으면(좌표를 먼저 보면) **라인 밖에 세운 휠체어를 영영 못 잡는다.** 반증 F2 가
정확히 그 파손이고, 전체 1372 중 **1 it 만** 빨간불이 된다 — 경계값 테스트(F1 이 9 it)와
판정 순서가 서로 대신 걸러 주지 않는다는 확인이다.

### 19.3 경계의 출처를 `model/court.ts` 에 둔 이유

`isOnSurface(mode, p)` 를 편집기가 아니라 코트 정의 옆에 뒀다. 마진 폭은 이미 한 번
바뀐 값이고(1.0 → 1.5 m), 편집기에 `37.5` 를 다시 적으면 다음에 바뀌는 날 두 곳이 갈라진다.
`court.test.ts` 의 새 it *'경계는 COURT_DEFS.surface 를 그대로 읽는다'* 가 세 코트 전부에서
"surface 안 = true / 한 픽셀 밖 = false" 를 **정의로부터 유도해** 대조한다.

파생 결정 둘:
- **라인 위(경계선)는 경기면으로 친다.** 선 위에 세운 개체를 고무줄로 걸 수 없으면 판이
  *"선 위에 놓지 마라"* 라는 규칙을 몰래 만드는 셈이다.
- **`flat` 에는 테두리가 없다.** surface 가 viewBox 전체라(D12) 마진이 0 이고, 판 이동은
  viewBox 밖에서만 열린다. 이것이 F1(경계를 viewBox 로 바꾸는 파손)에서 flat 테스트만
  초록불로 남는 이유이고, 그 초록불이 곧 대조군이다.

### 19.4 `pan` 판정은 컨트롤러가 내고 세션은 CourtStage 가 연다 (§8 소유권)

`PointerDownResult` 에 `pan?: boolean` 을 더했다. CourtStage(render-stage)는 §8 상 physics
런타임을 부르지 못해 **무엇을 잡았는지 모른다** — "여기는 마진이다" 를 스스로 판단하면 위
§19.2 의 사고가 그대로 난다. 그래서 판정은 컨트롤러가, 실행은 무대가 한다.

무대 쪽에서 정한 것 넷:
1. **더블클릭 무장 이동과 같은 세션에 합류시킨다.** 미는 코드가 두 벌이 되면 부호·클램프가
   언젠가 갈라진다. 다만 무장(`panArmed`)은 건드리지 않는다 — 마진을 한 번 끌었다고 코트
   안까지 이동 모드가 되면 다음 선택이 통째로 사라진다.
2. **rAF 물리 틱을 열지 않는다.** 이 드래그가 미는 것은 개체가 아니라 판이다(§6.1 규칙 1).
   대조군을 같은 대기 길이로 둬서 "0회 불렸다" 가 *스파이가 안 걸렸다* 로 통과하지 못하게 했다.
3. **down 을 전달했으면 up 도 전달한다.** 단, 판을 **실제로 민** 뒤에는 `client=null` 로 넘긴다 —
   이 저장소에서 `null` 은 이미 *"손을 뗐지만 탭이 아니다"*(pointercancel) 라는 뜻이라 새 신호를
   만들 필요가 없었다. 그래서 마진을 끌고 나서 선택이 풀리지 않고, **제자리에서 톡 치면**
   빈 곳 탭과 똑같이 풀린다([A-3] 해제 경로 보존 — 지금까지 그 일은 크기 0 짜리 고무줄이 했다).
4. **핀치로 끊길 때 이동 세션을 지운다.** `endInteraction` 이 `panFromRef` 를 안 지우면 활성
   포인터만 사라진 채 세션이 살아남아 **다음 드래그가 선택 대신 이동이 된다**(손을 뗄 때 그
   세션을 지울 주인이 없다). 더블클릭 이동에도 있던 구멍이라 이번에 함께 닫았다.

### 19.5 Ctrl/Cmd + 방향키 — 이미 차 있던 자리를 피한 경로

방향키 소비자를 전수로 세면 다섯이다: 전역 스텝 이동(←→) · 개체 이동 · 배치 커서 ·
**Shift+방향 = 화살표 끝점(1.11 이 이미 썼다)** · Alt+방향 = 개체 순회. 남은 것은 Ctrl/Cmd 뿐이고
계획서 지시도 그것이다. 그런데 **비어 있다는 것만으로는 부족했다** — 앞의 두 층이
`stopPropagation` 으로 전역(document)까지 못 가게 막고 있었다:

- `EditorStage.handleObjectKeyDown` — 개체에 포커스가 있으면 방향키·Delete·Enter 를 전부 먹는다.
- `EditorStage.handleContainerKeyDown` 의 §7.5d 배치 커서 — 배치 도구 + 코트 포커스면 방향키를 먹는다.

둘 다 맨 앞에 `if (e.ctrlKey || e.metaKey) return;` 를 넣어 흘려보낸다(preventDefault 도 하지
않는다 — 판정은 전역이 한다). 배치 커서 쪽이 특히 필요하다: **화면 밖 자리에 놓으려면 그때야말로
판을 밀어야 한다.** 이 두 층은 `BoardScreen.test.tsx` 가 문다 — 단언이 "개체가 안 움직였다" 만이
아니라 **"그 키가 document 까지 올라왔다"** 이고, 대조군으로 *수식키가 없으면 개체가 먹고 document
까지 가지 않는다* 를 같은 it 안에 둔다(§7.5d 계약이 그대로 살아 있다는 확인이기도 하다).

부호는 **창이 키 방향으로 간다**(오른쪽 키 → 판의 오른쪽이 보인다). 포인터로 테두리를 잡아
끄는 쪽은 반대(판이 손을 따라온다)인데, 그 반전은 *손이 판을 쥐고 있다*는 감각에서 나오고
키에는 쥘 것이 없다. 가장자리 자동 밀기가 이미 *"창이 손을 따라간다"* 로 같은 편이다
(`edgePanVelocity` 주석). 걸음은 `INTERACT.keyPanStepCssPx = 64` — **화면** CSS px 이라 배율이
달라져도 손이 느끼는 걸음이 같다(`settleSnapCssPx` 와 같은 이유).

`macOS 의 Cmd+←/→ 는 브라우저 뒤로/앞으로`라 `preventDefault` 로 막는다. 막지 않으면 판을
밀려던 손짓이 화면을 통째로 떠난다 — 그 한 줄만 지우는 반증(F8)이 1 it 을 빨간불로 만든다.

**남은 충돌 하나(다음 사람에게):** 2.10 의 스텝 칩을 **집은(held) 동안**에는 칩이 ←/→ 를
`stopPropagation` 으로 먹으므로 그때는 Ctrl+방향키가 판을 밀지 않는다. 집힌 상태는 의도된
모달 포획이라(“집힌 칩은 ←/→ 를 자기가 먹는다”) 예외를 뚫지 않았다. 뚫을 이유가 생기면
`TransportBar.onChipKeyDown` 의 `held` 분기 앞에 같은 한 줄을 넣으면 된다.

### 19.9 F6 이 드러낸 헛통과 — 고정 판정을 돌려주는 스파이는 세션 누수를 못 잡는다

*'핀치로 끊긴 뒤 다음 끌기는 다시 고무줄이다'* 의 첫 판본은 스파이 컨트롤러가 **늘 같은
판정**(`{ pan: true }`)을 돌려줬다. 그래서 낡은 세션이 남아 있든 없든 세 번째 pointerdown 이
새 이동 세션을 열었고, "판이 밀렸다" 는 두 경우 모두 참이었다 — **파손을 걸어도 초록불**이었다.

고친 방법: 스파이의 판정을 **세션마다 갈아끼울 수 있게** 하고, 끊긴 뒤의 새 세션에는
`{ edgePan: true }`(= 고무줄)를 준다. 이제 판이 밀리면 그것은 오직 낡은 세션이 살아남았다는
뜻이다. 대조군으로 *같은 자리에서 판정을 이동으로 되돌리면 실제로 밀린다* 를 같은 it 에 뒀다
(무대가 죽어서 통과하는 경우를 막는다).

**교훈:** "상태가 남았는가" 를 재는 테스트에서 스파이가 고정값을 돌려주면, 그 고정값이
남은 상태와 같은 결과를 만들어 판정을 통째로 무력화한다. 다음 사람이 세션·플래그 누수를
잴 때는 **두 번째 세션의 입력을 첫 번째와 다르게** 두어라.

## 20. 2.12 3 m 링(2-on-1) + 2인 규칙 위반 판정 (P2-4) — 착수 후 기록 (2026-08-12)

### 20.0 계획서 한 줄 요약보다 **규칙이 좁다** — 이 항목의 가장 큰 이탈

계획서 §4.4 P2-4 는 *"같은 팀 둘이 그 안에 들어가면 링이 붉어진다"* 라고 적었다. 그대로 만들면
**패스 훈련에서 링이 상시 붉다** — 같은 팀 둘이 공 근처에 있는 것은 반칙이 아니라 훈련의 기본
모양이기 때문이다. 계획서 §9-② 가 근거로 삼은 그 원문 대조 노트(2ndBrain『FIPFA 공식 규격
(2025) — SPIN 대조』§4·§5)가 조건과 **예외 둘**을 이미 적어 두고 있다:

| 규칙 | 조항 | 성립 조건 | 이 커밋의 판정 |
|---|---|---|---|
| **2-on-1** | Law 11 | 공 3 m 안에 같은 팀 2명 **+ 상대 1명 이상**. 예외 ① 그 인원 중 **골 지역 안의 골키퍼**는 세지 않는다 · 예외 ② 3 m 안에 상대가 없으면 성립하지 않는다 | `ringViolation()` 이 셋 다 구현 |
| **골 지역 3인** | Law 11 | 골 지역 안에 같은 팀 **3명 이상**(골키퍼 포함) | `zoneViolation()`. 문턱은 `GOAL_AREA_MAX = 2` **초과** |

**두 군데서 규정보다 넓게 판정한다. 모델에 팀↔골대 배정이 없기 때문이다**(`CourtDef.ruleZones`
는 좌·우 사각형일 뿐이고 `ChairDef` 에도 방어 방향이 없다):

1. 예외 ①의 *'자기'* 골 지역 → **아무 골 지역**으로 읽는다.
2. 골 지역 3인의 *'수비'* 팀 → **팀 무관**으로 읽는다(3명이 몰리는 쪽은 사실상 수비다).

팀↔골대 배정을 지어내는 것보다 넓게 재고 그 사실을 적어 두는 편이 낫다 — **규칙을 잘못
가르치지 않는 것**이 이 판의 목적이고, 그것이 §9-⑧ 이 센터 서클을 지우기로 한 근거와 같은
기준이다. 배정을 넣고 싶다면 그건 모델 확장(3.2 교육 필드)이지 이 항목이 아니다.

그리고 **이 판정은 경고이지 판결이 아니다.** 원문은 *"위치 자체는 반칙이 아니고 두 번째 선수가
능동적 플레이에 관여할 때 성립"* 이라고 못박는다 — 정지한 판에서 '관여'는 알 수 없다. 그래서
발화 문구가 *"… — 2-on-1 주의"* 다.

### 20.1 사전 등록 밖에서 깨진 것 — 1건. **그리고 그건 회귀가 아니다**

`EditorWorkspace.narrow.test.tsx` 의 *'넓은 창의 판 DOM 이 2.3 이전과 바이트 동일하다'* 해시가
빨간불이 됐다. §16.1 은 이 해시가 **2.4 가 트레이를 키울 때** 깨진다고만 등록해 뒀으므로 이번
원인은 등록 밖이다. §16.1 이 함께 적어 둔 판별 절차를 그대로 밟았다:

1. 먼저 **원인을 분리**했다 — `EditorWorkspace` 의 `rules={rules}` 한 줄만 빼고 다시 렌더하니
   해시가 **옛 값(`671f28…`)으로 정확히 돌아왔다.** 즉 같은 트리에 있던 2.6 의 미커밋 작업은
   이 DOM 을 한 바이트도 건드리지 않았고, 깨진 원인은 100% 이 커밋이다.
2. **HTML 전수 diff** 를 떴다(태그 단위 SequenceMatcher). 결과는 **삽입 1건**뿐:
   `<g aria-hidden="true" pointer-events="none">` 규칙 층. 빈 전술판이라 공이 없어 링은 0개이고
   골 지역 표시 2개가 `opacity="0"` 으로 숨어 있다. **삭제·변경 0건.**
3. 상자 뼈대 스냅샷은 **한 줄도 안 움직였다**(그 테스트는 무수정 초록불) — 규칙 층은 코트
   `<svg>` 안이라 크롬 예산의 어느 행도 먹지 않는다.

그래서 해시만 새 값(`c0d8dc32…`)으로 갱신하고, 테스트 주석에 *"세 번째 갱신은 2.12"* 와 diff
내용을 적었다. **§3 에 "판 DOM 에 층을 더하는 모든 항목" 행을 추가**해 다음 사람이 같은 판별을
반복하지 않게 했다.

### 20.2 새로 '의도적으로 깨질' 것 — 1건 (§3 에 등록)

`PresentStage.rules.test.tsx` 의 *'[결정 ⑧] 아직 남아 있는 센터 서클과 반지름이 같다'* 는
**5.3 이 센터 서클을 지우는 순간 빨간불**이 된다(`circle[r="75"][cx]` 가 사라진다). 갱신이
아니라 **삭제**가 답이다 — 두 원이 겹쳐 보이는 구간이 끝나면 그 계약 자체가 소멸한다.

이 it 을 굳이 만든 이유: 결정 ⑧ 이 *"지금 지우지는 마라(5.3 의 몫)"* 라고 했으므로 **겹쳐 보이는
상태가 실제로 존재하는 구간**이 있고, 그 구간에서 두 원이 구별되는지는 말이 아니라 단언으로
남아야 한다. 실측도 이 자리에서 나왔다 — 테스트를 처음 쓸 때 `circle[r="75"]` 선택자가 **센터
서클을 먼저 잡아** 5건이 한꺼번에 빨간불이 됐다. 두 원의 반지름이 정말 같다는 증거다.

### 20.3 시각 언어 — 왜 "붉게" 로 끝내지 않았나

붉은색(#ff5a5a)은 코트(#1f7a46) 위 대비가 **1.75:1** 이다(§7.1 비텍스트 3:1 미달). 계획서의
*"링이 붉어진다"* 를 글자대로 구현하면 **위반 표시가 가장 안 보이는 표시**가 된다. 그래서 채널을
셋으로 나눴다:

| 채널 | 깨끗함 | 위반 | 왜 |
|---|---|---|---|
| 모양 | 검정 케이싱(불투명, 코트 위 3.93:1) | 그대로 | 색을 못 봐도 **원이 거기 있다**는 것은 언제나 읽힌다 |
| 선 | 흰 파선 `8 6` | **실선** | 색각과 무관한 두 번째 채널. 파선/실선은 규칙/코트 구분과 같은 눈금이다 |
| 색 | 흰색(5.34:1) | 붉은색 | 세 번째. 케이싱 위에 얹히므로 국소 대비 6.9:1 로 읽힌다 |

여기에 **라이브 리전 발화**(§20.4)가 네 번째 채널이다. `ARROW_CASING` 이 알파 검정을 버리고
불투명 검정을 쓴 것과 같은 근거를 그대로 따랐다(colors.ts 의 검산).

**센터 서클과의 구별**도 이 언어가 담당한다 — 코트는 실선, 규칙은 파선 + 케이싱, 그리고 링은
**움직인다**. 5.3 이 오기 전까지 공이 센터에 왔을 때 이 셋이 두 원을 갈라 준다.

### 20.4 [D-6] 라이브 리전 — 시연은 개체를 `aria-hidden` 으로 감춘다

`PresentStage` 는 캐스트 전량을 `<g aria-hidden="true">` 안에 넣는다. **시각 신호만 두면 시각장애
코치에게 규칙 위반이 통째로 전달되지 않는다.** 그래서 위반이 **시작되는 순간** 한 번 말한다:

- `공 3 m 안에 레드 2명 이상 — 2-on-1 주의`
- `골 지역에 블루 3명 이상 — 3인 반칙`

문구의 인원 수는 `RING_SAME_TEAM_MAX + 1` · `GOAL_AREA_MAX + 1` 에서 **파생**한다(문턱을 고치면
발화가 따라온다). 팀 이름은 드릴의 `teams[side].label` 이다.

발화 규율 셋 — 전부 반증으로 확인했다:
1. **이어지는 같은 위반은 다시 말하지 않는다.** 60fps 로 60프레임을 흘려도 1회다.
2. **조합이 바뀌면 곧바로 말한다**(링만 → 골 지역). 새 정보이기 때문이다.
3. **해소는 말하지 않는다.** 드래그 한 번에 두 번 말하게 되고, 그것이 2.11 [D-7] 이 잠근
   이중 통보다. 대신 문턱 위에서 떠는 개체가 발화를 연타하지 못하도록 **400ms 히스테리시스**
   (`RULE_CLEAR_MS`)를 뒀다 — 깨끗한 상태가 그만큼 이어져야 다음 발화가 무장된다.

### 20.5 2.11 소리 어댑터를 쓸 것인가 — **안 쓴다**

계획서가 판단하라고 남긴 자리다. 결론은 **쓰지 않는다**이고, 근거 셋을 소스 계약 테스트로
잠갔다(`ruleOverlay.test.ts` 의 마지막 describe — 규칙 두 파일이 `cues` 를 import 하지 않는다.
같은 grep 이 실제 소비처(`useEditorPointer.ts`)는 찾아낸다는 **대조군**을 함께 둔다):

1. 2.11 의 세 신호는 전부 **손이 판에 닿는 순간**이다(놓임·막힘·트레이 반환) — 한 동작에 한 번
   울린다. 규칙 위반은 동작이 아니라 **상태**라, 문턱 위에서 드래그하면 한 드래그 안에서 여러 번
   켜졌다 꺼진다(그래서 발화 쪽에 히스테리시스가 필요했다). 소리에 같은 장치를 또 다는 것은
   신호가 아니라 소음을 만드는 일이다.
2. 시연 재생은 스텝마다 위반을 여러 번 지나간다 — 코치가 설명하는 동안 계속 울린다.
3. [D-6] 이 요구한 발화와 **같은 사건**을 두 채널로 통보하게 된다. 2.11 이 [D-7] 로 잠근 것이
   정확히 그것이다.

실기(0.5)에서 *"눈을 떼고도 알고 싶다"* 가 확인되면 얹을 자리는 `ruleOverlay.ts` 의 `announce()`
하나다 — 이미 "언제 한 번 알릴 것인가" 가 거기 모여 있다.

### 20.6 60fps 계약을 어떻게 지켰나 — writer 를 **둘로** 나눈 이유

| 무엇 | 누가 쓰나 | 왜 |
|---|---|---|
| 링의 **위치** | `TransformWriter` 팔로워(`registerFollower`) | 계획서 지시 그대로. ZoneHandles 가 React 로 좌표를 계산했다가 '핸들만 제자리에 남은' 전례가 이 자리다 |
| 링의 **색·표시**, 존 표시 | `ruleOverlay.ts` (새 writer) | TransformWriter 는 id 하나의 **자세**만 안다. 2-on-1 판정은 그 프레임의 **모든 선수**를 봐야 하므로 프레임 전체를 받는 소비자가 따로 필요하다 |

**React state 는 0 이다.** 한 곳만 예외인데 그건 프레임 값이 아니다 — `PresentStage` 가 *어느
스텝인가*를 state 로 들고 링을 그릴 공을 고른다(스텝이 바뀔 때만 갱신된다. 그 파일은 화살표·메모를
원래 매 프레임 state 로 다시 그리고 있어 리렌더 빈도가 늘지 않는다).

**`scaleWithHeld:false` 를 TransformWriter 에 새로 뚫었다.** 팔로워는 잡힘 배율 1.06 을 함께
받는데, 링은 **길이 자체가 의미**다 — 공을 잡으면 3 m 가 3.18 m 로 그려지고 판정은 75px 그대로라
"둘이 안에 있는데 링이 안 붉다" 가 **눈에 보인다.** 존 핸들은 반대로 칩과 함께 커져야 하므로
기본값은 `true` 이고 기존 호출부는 한 줄도 안 바뀌었다.

### 20.7 두 경로에 각각 배선 — 그리고 **한 프레임을 두 번 읽지 않는다**

| 경로 | 프레임 출처 | 판정 호출 자리 |
|---|---|---|
| 편집기 | `world.read()` (물리) | `usePhysicsRenderLoop` — `writeFrame(frame)` 바로 다음에 `rules.write(frame)` |
| 시연 | `sampleDrill(...)` (결정론적 보간) | `PresentStage.applyFrame` — 캐스트 좌표를 얕은 표 하나에 모아 넘긴다 |

편집기에서 판정 쪽이 `read()` 를 한 번 더 부르면, 물리 루프(§5.8 — 앱 rAF 와 **별개 인스턴스**)가
그 사이에 한 스텝을 돌 수 있어 링 위치와 색이 한 프레임씩 어긋난다. 그래서 **같은 객체**를 두
소비자에게 넘기고, 그 참조 동일성을 테스트가 잡는다(F9).

**마운트 순서 함정 하나를 실제로 밟았고 고쳤다.** 시연은 첫 프레임을 **레이아웃 이펙트**에서
흘리는데, 링·존 등록과 `setContext` 는 그보다 **뒤에** 오는 패시브 이펙트다 — 그 시점의 판정에는
아무 노드도 문맥도 없다. 일시정지로 열린 시연이라면 다음 프레임이 오지 않으므로 **1스텝의 반칙이
영영 발표되지 않는다.** 그래서 writer 가 마지막 프레임을 기억하고 `setContext` 가 그것으로 곧바로
다시 판정한다(TransformWriter 가 `register` 때 마지막 프레임을 즉시 기록하는 것과 같은 규율).
덤으로 **규칙 표시를 지금 켜는 순간** 다음 프레임을 기다리지 않고 판정이 선다.

### 20.8 스위치를 새로 만들지 않았다

표시·판정·발화 전부 **기존 `prefs.showRuleZones` 하나**에 걸었다. 근거 둘: (a) 3.0(★E-6)이 prefs
스키마 확장을 한 커밋에 모으라고 했으므로 여기서 필드를 늘리지 않는다. (b) 규칙 존을 감춘 사람에게
규칙 경고만 남기면 *"무엇이 말하는지 알 수 없는 소리"* 가 된다.

방어선은 **둘**이다 — 꺼지면 오버레이가 아예 렌더되지 않고(등록 0), `write()` 자체도 문맥의
`enabled` 로 되돌아간다. F14 가 그 둘을 갈라 보여준다: `write()` 의 게이트만 없애면 단위 테스트
1건만 빨간불이고 화면 테스트들은 초록불로 남는다(노드가 없으므로). 편집기는 rAF 마다 `write` 를
부르므로 그 두 번째 방어선이 실제로 일을 한다.

**`haptic` 을 따로 두지 않은 것이 이 항목의 유일한 설계 판단이다.** `ui/cues.ts` 머리말 ③ 이
*"소리와 진동은 **한 스위치**다 … 둘을 같은 if 에 묶으면 태블릿 무음 모드에서 신호가 통째로
사라진다"* 라고 못박아 뒀다 — 그 문장이 독립시킨 것은 **출력 채널**이지 설정이 아니다. 필드를
쪼개면 스피커 없는 기기에서 *'소리 끔 + 진동 켬'* 이라는, 사용자가 화면에서 구분할 수 없는 두
상태가 생긴다. 이 판단을 말로만 남기지 않으려고 단언을 하나 세웠다 — *'haptic 은 독립 필드가
아니다'*(`Object.keys(a11y)` 에 `haptic` 이 없고, **대조군으로 `sound` 는 있다**). 6.2 가 접근성
섹션을 정렬할 때 이 자리를 다시 볼 것이므로 근거가 코드 옆에 있어야 한다.

`tray` 를 드릴이 아니라 prefs 에 둔 이유: 판마다 서랍 상태가 다르면 **표적 좌표가 판마다
달라진다.** §3 불변식 1(*"접힌 것은 위치를 옮기지 않는다"*)이 지키려는 것이 정확히 그것이다.

### 21.1 스키마를 **올리지 않아도** 데이터는 안 죽는다 — 그런데도 올린 이유

`validatePrefs` 는 필드별 방어라 없는 키를 기본값으로 접는다. 2.11 이 `a11y.sound` 를 스키마
상승 **없이** 넣은 것도 그래서였다(prefs.test.ts 의 그 describe 머리말이 근거를 적어 뒀다).
같은 논리로 이번 세 필드도 상승 없이 넣을 수 있었다. 올린 이유는 셋이다.

1. **4.1 backup 봉투가 prefs 를 실제로 담는다.** 봉투는 *"payload 가 자기 버전을 들고 있다"* 를
   전제하는데(`transfer.ts:1-3`), 필드가 늘어도 버전이 그대로면 그 전제가 거짓말이 된다.
2. **E-6 이 막으려던 사고가 바로 그것이다.** 3차와 5차가 각자 필드를 넣고 각자 안 올리면,
   *"v1 인데 tray 가 있는 파일"* 과 *"v1 인데 tray 가 없는 파일"* 이 동시에 존재하게 된다.
3. 체인이 **비어 있는 채로 5차까지 가면 첫 마이그레이션을 아무도 실행해 본 적이 없는 상태**로
   맞게 된다. 지금 1→2 를 돌려 두면 `migrateDoc` 의 prefs 경로가 실측된다.

비용도 적어 둔다: `savePrefs` 가 이제 `schemaVersion: 2` 를 쓰므로, **옛 번들로 되돌아가면
too-new 판정에 걸려 설정이 통째로 기본값으로 리셋된다.** 이건 새 정책이 아니라 기존
정책(`loadPrefs` 의 *"구조를 신뢰할 수 없어 완전히 기본값으로"*)의 첫 발동이다.

그리고 마이그레이션 함수가 기본값을 `storage/prefs.ts` 에서 끌어오지 않고 **리터럴로 박은** 것은
게으름이 아니다 — (a) `prefs.ts → migrate.ts` 방향이 이미 있어 반대는 순환이고 (b) 마이그레이션은
*그때의* 기본값을 적어 둔 역사라, 나중에 `makeDefaultPrefs` 가 바뀌어도 과거 문서의 해석이 따라
바뀌면 안 된다. 그래서 **테스트도 `makeDefaultPrefs()` 가 아니라 리터럴 `false` 로 단언**한다.

### 21.2 `theme` 불변식은 **테스트가 부트 스크립트를 재현**해서 지킨다

`index.html:26-33` 은 첫 페인트 전에 **마이그레이션을 거치지 않은 날것의 localStorage** 를 읽는다.
그래서 "loadPrefs 가 light 를 돌려준다" 는 이 불변식의 증명이 못 된다 — 부트 스크립트는
`loadPrefs` 를 부르지 않는다. 테스트에 그 스크립트를 **같은 리터럴 키·같은 3항 연산자로**
옮겨 심고(`bootScriptTheme()`), 저장된 JSON 의 최상위에 `theme` 이 문자열로 있는지도 따로 본다.

`PREFS_KEY` 상수 대신 `'spin.prefs'` 리터럴을 쓴 것이 핵심이다. 상수를 쓰면 키를 바꿔도 테스트가
같이 따라가 초록불이 나고, 부트 스크립트만 조용히 어긋난다. 그 대신 *'저장 키는 리터럴
spin.prefs 다'* 단언을 하나 세워 `PREFS_KEY` 쪽이 움직이면 잡히게 했다.

### 21.3 사전 등록 밖에서 깨진 것 — **0건**. 새로 등록한 것 — 1건

1393 → **1422**(+29), 실패 0. 기존 테스트는 한 줄도 고치지 않았다 — `validatePrefs` 가
`Preferences` 로 타입된 객체 리터럴을 조립하므로 **필수 필드를 빠뜨리면 tsc 가 먼저 잡는다**
(F1 에서 실측: `TS2741 Property 'tray' is missing`).

> ⚠️ **3.2 는 이 안전망을 못 쓴다.** `validate.ts:429-445` 의 드릴 조립부는 `description` 처럼
> **선택 필드를 `...(x !== undefined ? { x } : {})` 로 스프레드**하는데, 선택 필드는 빠뜨려도
> 타입 에러가 **안 난다.** 교육 필드를 optional 로 넣는 순간 "저장 → 다시 읽기" 왕복 테스트
> 말고는 증발을 잡을 방법이 없다. 3.2 착수자는 이 문장을 먼저 읽어라.

새로 '의도적으로 깨질' 것은 §3 표에 등록했다 — *'스키마는 딱 한 칸 올랐다 — 2 다'* 1 it 이

`CURRENT_PREFS_SCHEMA` 파생이라 자동으로 따라오므로 **그쪽을 리터럴로 고치면 가드가 죽는다.**

## 22. 3.1 STEP_META 입력 UI — 착수 후 기록 (2026-08-12)

### 22.0 이 항목의 정체 — *"부품은 다 있고 스위치만 없었다"*

`STEP_META` 리듀서(reducer.ts:167-176) · 병합 키(history.ts:33-34) · `COALESCE_TYPES` 등록
(actions.ts:81) · `validate.ts` 화이트리스트의 `name`/`note`/`durationMs`(:407-417) · 시연 자막
(PresentRunner.tsx:497-501) 이 **전부 미리 만들어져 있었고 dispatch 하는 곳만 0** 이었다.
그래서 이 항목의 새 코드는 입력 세 칸이고, 나머지는 **이미 있던 배선이 실제로 이어지는지**를
증명하는 일이다. 그 증명을 단위 테스트로 조각내면 이음매 하나가 끊겨도 전 조각이 초록불이므로
(지금까지가 정확히 그 상태였다), 새 스위트는 화면 끝에서 끝까지 **한 줄로** 본다:

> 하단 칩으로 스텝을 고른다 → 인스펙터 [스텝] 구역에 적는다 → `STEP_META` → 자동저장 → IDB
> 왕복(validate) → 시연 화면이 그 문장을 읽는다.

### 22.1 계획서 지시에서 벗어난 것 — 1건

| 지시 | 한 것 | 왜 |
|---|---|---|
| *"스텝 칩 1탭 → 인스펙터 **[스텝] 탭**"* | 칩 1탭은 **스텝 선택** 그대로 두고, 인스펙터 **맨 위 구역**을 그 스텝 편집기로 만들었다. 칩을 누른다고 인스펙터가 열리지는 않는다 | 칩 탭마다 오버레이가 열리면 세로 화면에서 판의 62% 가 덮인다 — 2.2 가 인스펙터를 기본 접힘으로 내린 근거(§5.2 축척 손해)를 칩이 매번 무효로 만든다. 그리고 완료 판정의 `key={step.id}` 요구 자체가 **인스펙터를 연 채 칩으로 스텝을 넘기는** 사용을 전제한다 — 그 사용에서 1탭이 성립한다. '탭(tab)' UI 부품은 인스펙터에 없다(구역+구분선이 이 패널의 관용구다); 3.4 의 [개체] 탭이 오면 그때 함께 만드는 편이 두 번 짓지 않는다 |

더한 것 2건: (a) **시간 칸 되비침**(아래 22.3) (b) 구역을 **맨 앞**에 둔 것 — 인스펙터를 여는
가장 잦은 이유가 "지금 이 스텝의 자막"인데 오버레이 시트는 세로에서 `min(340px, 62%)` 라 아래
구역은 굴려야 닿는다. 제목·난이도는 드릴당 한 번 적고 마는 값이라 뒤로 물러났다.

### 22.2 비제어 입력 + `key={step.id}` — 제어로 안 간 이유

완료 판정이 지목한 함정(`:305-310`·`:105-111` 에 없던 key)은 **비제어(defaultValue) 입력에서만**
성립한다. 제어(value)로 바꾸면 key 는 무의미해지고 함정도 사라지지만, 글자마다 React 가 DOM
value 를 되쓰면서 **한글 IME 조합**에 손을 댄다 — 입에 젓가락을 물고 치는 사용자에게 조합이
끊기는 것은 그대로 오타다. 그래서 패널의 관용구(비제어)를 따르고 세 입력 모두에 key 를 달았다.

**대가는 적어 둔다**: 되돌리기로 값이 바뀌면 화면에는 옛 글자가 남는다(이 패널의 다른 비제어
입력 전부가 같다). key 를 `epoch` 로 바꾸면 해결되지만 그러면 **판 조작마다** 입력이 재마운트돼
포커스가 날아간다. 단, 입력에 포커스가 있는 상태의 `Ctrl+Z` 는 `useEditorKeyboard:58` 의
editable 가드가 네이티브 undo 로 넘기고 그 네이티브 undo 는 `input` 이벤트를 내므로 모델이
따라온다 — 어긋나는 것은 **포커스를 뗀 뒤 헤더 [되돌리기]를 누른 경우**뿐이다.

### 22.3 dispatch 는 blur 가 아니라 change 다 — 이 패널에서 유일하다

이 패널의 다른 입력은 전부 `onBlur` 로 한 번 쏜다. 스텝 메타만 `onChange` 인 이유가 둘:
(1) 적는 동안 하단 칩 라벨(`스텝 n: 이름`)과 스텝 목록이 따라 움직여야 무엇을 적고 있는지 판에서
보인다. (2) blur 로 한 번 쏘면 `COALESCE_TYPES` 창(700ms/5s)이 **열릴 일이 없다** — 병합이 있으나
마나가 된다. 대신 글자마다 커밋이 쌓이는 것을 그 병합이 막는다(F3 이 그 반대편을 실측).

시간 칸만 `onBlur` 가 **하나 더** 붙는다: 초 → ms 변환에 상한 클램프(60초)가 있어 화면과 모델이
갈라질 수 있는 유일한 자리라, 손을 뗄 때 실제 저장값으로 되비친다. 없으면 화면은 "999초"라고
말하는데 재생은 60초로 돈다(F6).

### 22.4 새로 '의도적으로 깨질' 것 — 없다

기존 테스트 0줄 수정. 인스펙터 `<aside>` 에 `paddingTop:17` 이 생기고 `DrillInfoSection` 의
`padding` 이 `'17px 17px 0'` → `'0 17px'` 로 옮겨 갔지만(첫 구역이 showSteps 로 갈리므로 상단
여백의 출처를 껍데기로 올렸다), 전술판 스냅샷(`EditorWorkspace.narrow.test.tsx.snap`)은 인스펙터가
닫힌 첫 화면 뼈대라 바이트 동일이다. 표적 예산(2.5)도 [보드] 초기 상태 기준이라 불변 — 새 입력
3개는 **전술판에 없고**(`showSteps=false`) 오버레이 안에 있다.

| F1 | 이름 input 의 `key={step.id}` 제거 | 1 it | 칩으로 1장째에 돌아왔는데 이름 칸에 2장째 글자('전개')가 남는다 |
| F2 | **textarea** 의 `key={step.id}` 제거 | 1 it | 완료 판정이 지목한 그 자리. 메모 칸에 옛 스텝 글자가 남는다. F1 과 **따로** 찌른다 — key 는 요소마다 붙는 것이라 한쪽만 빠뜨릴 수 있다 |
| F3 | `COALESCE_TYPES` 에서 `STEP_META` 제거 | 2 it | 되돌리기 한 번에 `'측면 전'` 처럼 **한 글자만** 지워진다(= 글자마다 undo). 이 항목의 완료 판정 1번 |
| F4 | 병합 키를 `STEP_META:ALL` 로(스텝 id 제거) | 1 it | 대조군 it 이 잡는다: 1장째 타이핑까지 같은 칸으로 합쳐져 되돌리기 한 번이 **두 스텝을** 지운다 |
| F5 | 이름 dispatch 를 change → blur | 3 it | 적는 동안 칩 라벨이 안 따라오고, 병합창이 열리지 않아 되돌리기 테스트 2건도 함께 빨간불 |
| F6 | 시간 칸 blur 되비침 제거 | 1 it | 화면 `999` / 모델 `60000` 의 갈라짐. **대조군 초록불**: 범위 안의 값(3)은 손대지 않는다 |
| F7 | `validate.ts:411` 에서 `durationMs` 제거 | 1 it | 저장 → 다시 읽기에서 **조용히 증발**. 지시서가 경고한 화이트리스트 함정을 계기로 재현했다 |
| F8 | 같은 자리에서 `note` 를 `''` 로 | 1 it | 위와 같은 함정의 다른 필드. 세 필드를 따로 단언하는 이유 |
| F9 | 시연 자막의 `note` 문단 제거(PresentRunner) | 1 it | **repo 단언은 초록불인 채** 시연 단언만 빨간불 = 마지막 다리(IDB → 화면)가 실제로 계기에 물려 있다 |

**헛통과 하나를 실제로 잡았다**: 처음 F5 를 돌렸을 때 *'이름·메모를 적으면…'* it 은 **초록불**
이었다 — 이름을 친 뒤 곧바로 메모 칸으로 옮기는 바람에 그 이동이 blur 를 일으켜 dispatch 가
나갔기 때문이다. "적는 동안 따라온다"를 단언하려면 **포커스를 떼기 전에** 봐야 한다. 단언 순서를
고친 뒤 F5 는 3 it 을 빨간불로 만든다(위 표는 고친 뒤의 값이다).

**무한 루프로 뻗는 테스트는 없다** — 전부 화면 단언이고, 유일한 대기는 자동저장 flush 를 기다리는
`waitFor` 하나다(언마운트 동기 플러시가 이미 걸린 뒤라 폴링 1~2회에 끝난다).
