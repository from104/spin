## 1. 이 문서의 용법

재편(2.1 개명 · 레일 3단 · NavEntry 확장 · 1.3 자가 분리)을 실행하면 아래 §3 표의 테스트들이

그건 회귀다.** 작업 중 예상 밖의 빨간불을 만나면 "재편 중이라 원래 깨지는 것"이라고 넘기지 말고,

수정(특히 §4 의 수호 단언을 고치는 수정)도 회귀로 취급한다.

## 4. 수호 단언 — 절대 깨지면 안 되는 것 (0.4)

`src/app/screens.test.ts:13-18` 전문:

```ts
it("'editor' 는 더 이상 화면 키가 아니다", () => {
  // 2026-08-09 재편: 자유 전술판과 드릴 편집은 둘 다 home 자리에 뜬다(AppShell 의 StageTarget).
  // 이 단언이 없으면 어디선가 go('editor') 를 되살렸을 때 SCREEN_SET 이 걸러 조용히 무시하고,
  // 화면이 안 바뀌는 이유를 찾기 어려워진다.
  expect(SCREEN_ORDER).not.toContain('editor');
});
```

이것이 **이 안(안 1, Board-First)이 안 2(화면 분리안)와 갈리는 유일한 구조적 분기의 수호선**이다.
안 2 는 `board`/`edit` 로 화면 키를 쪼개며 2026-08-09 의 "editor 를 별도 화면 키에서 없앴다"
결정을 되돌리려 했다(계획서 2.1 원칙 1). 채택안은 개명만 하고 화면 키를 늘리지 않으므로,
`SCREEN_ORDER` 가 `['board','drills','present','settings']` 가 돼도 이 it 은 `SCREEN_ORDER` 와
문자열 `'editor'` 만 참조해 **손대지 않은 채** 통과한다.

**재편의 어느 커밋에서든 이 it() 을 수정하거나 삭제하는 diff 가 나타나면, 그 커밋은 안 2 로
미끄러진 것이다. 갱신 대상이 아니라 판정 기준이다.**

### 8.1 `selfSeparate.test.ts` 의 한 건이 **드래그 중 루프가 죽는 것**을 전제로 서 있었다

### 8.2 재현된 것 — 드래그 도중 정착 구간이 열리면 판이 언다

`resetGoals()` 는 `openSettle()` 을 부른다. 드래그 중이면 손이 멈춘 프레임이 곧
`allAtRest() === true` 라, 그 프레임의 정착 술어가 **루프를 꺼 버린다.** 실측(physicsProbe):
칩을 잡고 목표에 도달시킨 뒤 `resetGoals()` → 5 프레임 뒤 `isRunning() === false`, 그 뒤로
포인터를 x=205 → 600 으로 옮기고 60 프레임을 흘려도 칩의 x 는 **205 그대로**. 손을 떼도
`releaseDone` 이 평가되지 않아 `endDrag` 가 영영 안 오고, 칩은 `static` 인 채로 남아
이웃도 못 민다(다음 드래그의 `beginDrag` 가 옛 세션을 정리할 때까지).

로 적어 둔 바로 그 사고인데, 그 방어는 **"새 드래그가 옛 구간을 닫는다"** 쪽만 막고
**"드래그 도중 새 구간이 열린다"** 쪽은 비어 있었다. 조치는 `openSettle()` 한 곳:
세션이 살아 있으면 구간을 열지 않고 `loop.start()` 만 한다.

### 8.3 rAF 체인 분화 — `rafLoop.ts` 의 해지 함수가 예약을 접지 않았다

`raf.add` 의 해지 함수는 `subs.delete(fn)` 만 했다. 그래서 *"마지막 구독자는 나갔는데 예약은
아직 살아 있는"* 창이 프레임 하나만큼 열리고, 그 창에서 새 구독이 들어오면 `wasEmpty` 만 보고
**두 번째 체인**을 예약했다. 두 체인은 서로를 모른 채 각자 재예약하므로 영원히 둘로 남는다.
실측: 해지→재구독을 5번 반복하면 프레임당 콜백이 **1 → 6**. 창이 열리는 실제 경로는 같은
커밋 안의 언마운트→마운트(StrictMode 이중 호출 · 화면 왕복)와, 렌더마다 deps 가 바뀌는
rAF 구독 이펙트다. 조치: 구독이 0 이 되면 `cancelAnimationFrame` 으로 예약을 접는다.

**이것이 신고된 "편집 중 브라우저 멈춤" 이라는 증명은 없다.** 편집기에는
`usePhysicsRenderLoop` 의 상시 구독이 있어 구독 수가 0 으로 떨어지는 창이 마운트/언마운트
경계에서만 열린다 — 성장이 화면 왕복 횟수에 비례한다. 시연 화면(`PresentStage`)에는 상시
구독이 없어 훨씬 빨리 자란다. **이슈는 닫지 않는다.**

### 10.1 계획서가 센 네 겹 외에 **다섯 번째 원인**이 있었다 — 메모의 좌표를 아무도 쓰지 않았다

`NoteLabel` 은 다른 개체와 똑같이 `writer.register(id, el)` 로만 자리를 받는다. 그런데
메모는 물리 바디가 없어 `world.read()`(→ `usePhysicsRenderLoop` 의 매 프레임 writeFrame)에
없고, `store/editor/tween.ts` 의 `poseFrame` 에도 **빠져 있었다**(휠체어·공·콘 세 루프뿐).
즉 메모의 `<g>` 에는 `transform` 속성 자체가 붙은 적이 없다.

실측(임시 프로브): 코트 (300,200) 에 만든 메모의 `#obj-nt_*` 는 `transform === null`,
`poseFrame(step)` 의 `nt_*` 키는 **0개**. 그래서 코트 어디를 탭해 만든 메모든 전부 viewBox
원점 — 판 **왼쪽 위 마진**, 경기면(37.5,37.5) 바깥 — 에 그려졌다. 탭한 자리에는 아무것도
나타나지 않는다. 계획서가 센 네 겹(빈 텍스트 · 픽셀 0 · 링 없음 · setRing 미배선)을 전부
고쳐도 이것을 남기면 사용자에게는 **여전히 무반응**이다.

조치는 `poseFrame` 에 메모 루프 한 개를 더한 것뿐이다. 부수 효과로 스텝 전환 트윈(`frameAt`)이
메모도 보간하게 되는데, 메모는 `isId(id,'ch')` 가 아니므로 공·콘과 같은 선형 보간을 탄다.

### 10.3 (d) "히트 반경 ↔ 시각 크기 정합" 을 어디까지 참으로 만들었는가

**참으로 만든 것** — 빈 메모(= 신고된 그 메모): 그려진 32×24 칩의 **네 꼭짓점**이 실측 배율
전 구간(0.663 / 0.891 / 1.151 / 1.675 / 4.0)에서 1차 히트 원 안이다. 근거 숫자는 하나로 묶여
있다: 칩 외접원 = `NOTE.hitRadiusPx` = 20 < `NOTE.ringRadiusPx` = `HIT_R_MAX_PX.note` = 22.
테스트는 상수를 되읽지 않고 **DOM 의 `path` `d` 를 파싱해 꼭짓점을 얻어** 그대로 `hitTest` 에
넣는다 — 어느 한쪽 숫자만 바꿔도 반드시 빨간불이다.

**남긴 경계** — 글이 있는 메모의 칩은 글 길이만큼 **가로로** 늘어나므로, 그 양 끝은 반지름
22 짜리 원 밖이다. `§5.12 SceneSnapshot` 이 메모를 **점 하나**로만 들고 있어서(`{id, p}`)
반경이 상수일 수밖에 없는 구조적 한계다. 칩을 고정 크기로 만들면 이 한계는 사라지지만 긴 글이
칩 밖으로 새고, 반대로 per-note 반경을 주려면 넓은 칩의 외접원이 100 px 을 넘어(가로 200 px
칩이면 100.7) 우선순위 1 짜리 원이 판을 삼킨다. **정직한 답은 원이 아니라 회전을 아는 사각형
히트**인데 `HitContext` 에 `rot` 이 없다 — 1.9 의 범위를 넘는다. 지금 그 바깥은 select 도구의
2차 관대 패스(22/s 월드)가 부분적으로만 받는다.

### 10.4 `setRing` 을 무엇에 배선했는가 — "지금 잡고 있는 것" 의 링

`setRubberBand`·`setLeash`·`setGhost` 와 같은 가족(드래그 세션당 하나, 직접 DOM)으로 붙였다.
개체가 **선택**됐다는 표시로 쓰지 않은 이유: 오버레이 링은 하나뿐이라 다중 선택을 표현할 수
없다(러버밴드가 메모를 여러 개 고른다). 선택 링은 5종 개체가 각자 자기 `<g>` 안에 그린다 —
`NoteLabel` 도 이번에 그 규약에 합류했다.

오버레이 링이 개체 자신의 링과 겹쳐 그려지는데도 값이 있는 이유는 **가려짐**이다: 개체의 링은
자기 `<g>` 안이라 위 레이어(§3.5 콘 → 화살표 → 휠체어 → 공 → 메모)에 덮인다. 콘을 잡고 휠체어
밑으로 끌면 무엇을 잡았는지가 화면에서 사라진다. `SelectionOverlay` 는 `ObjectLayer` **뒤에**
그려지므로 절대 가리지 않는다. 그리고 메모에는 이것이 **유일한** 드래그 신호다 — 물리 바디가
없어 리시도 고스트도 뜨지 않는다(테스트가 `setLeash`/`setGhost` 미호출로 그것을 못박는다).
